# Сборка пакетов монорепозитория

В дизайн-системе **DXT UI** процесс компиляции всех взаимосвязанных пакетов монорепозитория полностью автоматизирован с помощью утилиты `dxt-build-packages`. Разработчику больше не нужно вручную определять порядок сборки модулей или тратить время на повторную компиляцию неизмененных пакетов.

Инструмент берет на себя весь сборочный конвейер, автоматически анализирует граф зависимостей через приоритеты и применяет инкрементальное кэширование.

## Преимущества автоматизации

### 1. Интеллектуальное кэширование и мгновенный инкрементальный билд
Команда `dxt-build-packages` отслеживает состояние собранных пакетов через локальный файл кэша `./logs/ui-build.log.json`. Если исходный код и версия пакета не изменялись с момента последней сборки, шаг компиляции мгновенно пропускается.

### 2. Гарантированный порядок сборки через приоритеты (`ui-priority`)
Каждый пакет в `package.json` может объявить свой сборочный приоритет `ui-priority`. Оркестратор строго упорядочивает сборку по возрастанию приоритета, компилируя фундаментальные базовые библиотеки (`functional`, `styles`, `constructor`) до зависимых от них компонентов (`d1`) и документации.

### 3. Автоматический выбор скрипта компиляции
Оркестратор самостоятельно определяет наилучшую команду сборки для каждого пакета по прозрачной цепочке приоритетов: `prepublishOnly` -> `build-recovery` -> `build`.

## Пошаговое руководство (Что нужно делать)

### Шаг 1. Настройте конфигурацию package.json
В файле `package.json` каждого пакета убедитесь в наличии скрипта сборки и при необходимости укажите приоритет `ui-priority`:

```json
{
  "name": "@dxtmisha/example-package",
  "version": "1.0.0",
  "ui-priority": 400,
  "scripts": {
    "build": "vite build",
    "prepublishOnly": "npm run build"
  }
}
```

### Шаг 2. Запустите команду сборки
Выполните команду `dxt-build-packages` в терминале:

```bash
npx dxt-build-packages
```

Сборщик просканирует директорию `packages/`, отсортирует найденные пакеты по приоритетам и скомпилирует только те, у которых изменилась версия:

```text
Build packages(14)...
Build packages changed: 2
```

Если ни один пакет не требует обновления, сборщик завершит работу без лишних действий:

```text
Build packages(14)...
Build packages - no changes
```

### Шаг 3. Изучите кэш сборки
После завершения процесса версии скомпилированных пакетов автоматически сохраняются в `./logs/ui-build.log.json`:

```json
{
  "@dxtmisha/functional-basic": "1.0.0",
  "@dxtmisha/functional": "1.0.0",
  "@dxtmisha/styles": "1.0.0",
  "@dxtmisha/constructor": "1.0.0",
  "@dxtmisha/d1": "1.0.0"
}
```

### Шаг 4. Пересборка при обновлении кода
Когда вы вносите изменения в пакет и обновляете его версию в `package.json`, повторный запуск `npx dxt-build-packages` автоматически обнаружит несовпадение с версией в логе и пересоберет только данный пакет.

## Управление приоритетами сборки (`ui-priority`)

Числовое свойство `ui-priority` в `package.json` задает последовательность компиляции. Чем меньше значение, тем раньше собирается пакет:

- **100 – 200 (Базовые утилиты и стили)**: Фундаментальные библиотеки без внешних зависимостей внутри монорепозитория (`@dxtmisha/functional-basic`, `@dxtmisha/functional`, `@dxtmisha/styles`).
- **300 – 400 (Абстракции и конструкторы)**: Ядро компонентов и протоколы (`@dxtmisha/constructor`, `@dxtmisha/mcp`).
- **500 (Стандартный приоритет)**: Библиотеки готовых UI-компонентов и дизайн-системы (`@dxtmisha/d1`, `@dxtmisha/figma`).
- **600 – 900 (Интеграции и документация)**: Верхнеуровневые потребители и сборочные приложения (`@dxtmisha/wiki`, `@dxtmisha/storybook`).

## Специальные параметры package.json

- **`ui-priority` (number)**: Вес пакета в очереди сборки (по умолчанию `500`).
- **`ui-test` (boolean)**: Если установлено в `true`, пакет считается тестовым и полностью исключается из процесса автоматической сборки.
- **Приоритет выбора скриптов**: Оркестратор проверяет `scripts` пакета и запускает первую найденную команду: `prepublishOnly`, затем `build-recovery`, затем `build`.

## Преимущества перед ручной сборкой

- **Экономия до 90% времени**: Компилируются только реально изменившиеся модули.
- **Исключение циклических и сломанных зависимостей**: Гарантированная сборка базовых библиотек до компонентов.
- **Чистый лог и прозрачность**: Полный учет текущего состояния сборок в локальном файле кэша.
