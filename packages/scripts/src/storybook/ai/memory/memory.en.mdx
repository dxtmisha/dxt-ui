# Local Package Memory (ai-memory.md)

The `ai-memory.md` file is a long-term memory mechanism for AI agents at the level of an individual monorepo package. It preserves architectural experience, design decisions, discovered constraints, and developer preferences across conversation sessions.

Unlike static global prompt files, package memory is dynamically curated during collaborative development and holds the highest local priority when making agent decisions.

## Why Local Memory is Essential in a Monorepo

In a complex monorepo with multiple independent packages (`@dxtmisha/d1`, `@dxtmisha/constructor`, `@dxtmisha/styles`, `@dxtmisha/functional`, etc.), different areas possess unique characteristics:

- **Context Isolation** — Rules and styling constraints of `@dxtmisha/styles` should not contaminate or complicate the context of `@dxtmisha/functional-basic`.
- **Preventing Repeated Mistakes** — When a developer points out a specific package quirk (such as avoiding tables in MDX for `@dxtmisha/scripts`), the agent records this constraint and never makes the mistake again.
- **Independence from Chat History** — When restarting context or beginning a new dialogue, the agent reads `ai-memory.md` as step one and immediately respects all local agreements.

## Strict Rules for Maintaining ai-memory.md

To maintain the clarity and efficiency of the workspace memory, strict rules are enforced:

- **Strict Local Placement**
  The `ai-memory.md` file must reside strictly in the root of the target package (e.g., `packages/scripts/ai-memory.md`). Placing package-specific directives in the repository-root memory file is forbidden.

- **Explicit Developer Trigger**
  The AI updates `ai-memory.md` **only** upon explicit developer command (keywords: "Remember", "Save to memory", "Запомни") or when finalizing critical architectural fixes.

- **Content Integrity & Deduplication**
  When adding a new rule, the agent is **only allowed to eliminate exact duplicates or resolve direct conflicts**. The content and wording of existing rules must not be modified, condensed, or rewritten. Deleting previously established rules and constraints is strictly prohibited.

- **Critical Architectural Rules Only**
  Recording routine changelogs, verbose chat conversations, or temporary scratch notes is prohibited. The memory file contains strictly actionable architectural constraints, typing contracts, and formatting guidelines.

- **Relative Paths**
  Only relative paths from the package root are allowed; absolute machine paths are forbidden.

## Example ai-memory.md File

```markdown
# AI Workspace Memory (packages/scripts)

This file contains package-specific guidelines for @dxtmisha/scripts.

## Guidelines
- Follow strictly all global development principles from root ai-prompt.md.
- Documentation formatting rules for Storybook:
  - Do NOT use horizontal lines (---).
  - Do NOT use markdown tables (| ... |) — format all structured items as bullet lists (- **Key**: description).
  - Focus on practical developer workflows and actions, not internal engine details.
```

## Comparing ai-memory.md with Built-in IDE Memories

Modern code editors and AI plugins (Cursor, Windsurf, Claude Code) provide built-in rules and memory mechanisms. However, for professional team workflows and design system maintenance, built-in editor memories suffer from three fundamental drawbacks:

- **1. Vendor Lock-in:**
  Memories stored inside Cursor do not migrate to Windsurf, Claude Code, GitHub Copilot, or Antigravity IDE. The `ai-memory.md` file uses standard Markdown, universally understood by any modern AI coding assistant.
- **2. Absence from Version Control (Git):**
  Built-in editor memories reside locally on an individual developer's machine and are not committed to Git. Consequently, when a new team member joins, their AI assistant starts with a blank slate and repeats previous mistakes. The `ai-memory.md` file is committed to Git, synchronizing engineering context across the entire team.
- **3. Lack of Modular Scoping (Package Scopes):**
  Built-in editor memory is typically global across the entire repository. In a monorepo, UI kit styling rules inadvertently pollute backend or utility context. The `ai-memory.md` file is strictly scoped to its own package directory.

## How to Use Memory in Your Workflow

- **Saving an Agreement:**
  Developer: *"Remember: across all storybook docs in this package, never use horizontal lines or markdown tables."*
  Agent: Appends the directive to the local `ai-memory.md` file of the current package.

- **Reading at Session Start:**
  Whenever assigned a task in a package, the agent follows the **Chronological Guard** protocol, reading `ai-memory.md` before taking any action.
