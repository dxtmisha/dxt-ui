Цель: Оптимизировать TypeScript-определения типов для деклараций в `File Content`.

ОБЛАСТЬ И КОНТЕКСТ:
- Обрабатывай СТРОГО сущности из `File Content`. НЕ добавляй неэкспортируемые сущности или код из `File JS Code`.
- Используй `File JS Code` ТОЛЬКО как справочник для понимания логики реализации при составлении JSDoc-описаний.
- ИИ-ассистенты по коду будут опираться ИСКЛЮЧИТЕЛЬНО на этот результат. Обеспечь полные контракты типов и понятные JSDoc-описания.
- НЕ включай в результат пути к файлам, ссылки или внутренние импорты.

ПРАВИЛА ДЛЯ JSDOC:
- ОБЯЗАТЕЛЬНО ДЛЯ ВСЕХ КЛАССОВ, МЕТОДОВ, ФУНКЦИЙ И АКСЕССОРОВ: Каждый `class`, `declare class`, `abstract class`, `function`, `declare function`, метод (public/static/abstract), `constructor`, а также `get`/`set` аксессор ДОЛЖЕН ВСЕГДА иметь JSDoc-описание.
  * Стиль: Описания ДОЛЖНЫ быть максимально понятными и информативными, но при этом максимально краткими и емкими. Избегай «воды».
  * Предпочтение однострочному формату: Предпочитай однострочный формат JSDoc (`/** Description @keywords search_terms */`) для экономии вертикального пространства и уменьшения размера файла.
  * Удаление `@param` и `@return` / `@returns`: СТРОГО УДАЛЯЙ теги `@param`, `@return` и `@returns` из всех JSDoc-комментариев.
  * Ключевые слова для поиска ИИ: Включай релевантные поисковые теги/ключевые слова (например, тег `@keywords` или поисковые термины), чтобы поиск по коду ИИ мог легко обнаруживать функционал.
  * Разрешенные теги: СОХРАНЯЙ ТОЛЬКО `@example`, `@remarks`, `@note`, `@warning` и `@keywords`. Удаляй `@param`, `@return`/`@returns` и все остальные теги.
  * Если JSDoc отсутствует: Сгенерируй понятный, краткий, оптимизированный для поиска JSDoc на английском языке на основе анализа `File JS Code`.
  * Если JSDoc уже есть: Оптимизируй, сожми, переведи на английский язык и примени правила тегов.
- ТИПЫ, ИНТЕРФЕЙСЫ И ENUM: Удаляй JSDoc для простых/очевидных типов; добавляй или сохраняй краткий JSDoc для сложных типов.
- Размещай JSDoc непосредственно над декларациями. Удаляй обычные строчные комментарии (`//` или `/* */`).

ОЧИСТКА И СТРУКТУРИРОВАНИЕ:
- Удаляй внутренние инструкции `import` и внутренние реэкспорты. Сохраняй экспорты внешних пакетов.
- Удаляй непубличный контент (приватные/защищенные члены, неэкспортируемые элементы). Сохраняй весь публичный API-интерфейс.
- НЕ удаляй определения `type`. Сохраняй абстрактные классы.
- Форматируй вывод плотно, без лишних пустых строк.

ФОРМАТ ВЫВОДА:
Верни ТОЛЬКО чистый TypeScript-код, соответствующий `File Content`. Никакого markdown, блоков кода (```) и текстовых пояснений.
